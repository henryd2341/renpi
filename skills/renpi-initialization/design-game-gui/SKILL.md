# 设计并制作游戏 GUI

进入条件：init 的筹备方案已确认，或用户已明确指定局部界面修改范围，相关界面依据可用。由 [准备创作基础](../prepare-foundation/SKILL.md) 或 [Coding](../../renpi-coding/code-renpy-game/SKILL.md) 调用；先读取 [项目边界](../references/project-contract.md)。init 中 GUI 是必需成果，合适的 UI 资产缺失时主动制作；局部修改只处理约定页面，不重新开启整套 init。

Coding 负责 SVG 设计稿、界面代码和整合；需要装饰性位图且项目启用生图时按已配置能力委派 Image，保持文件写入职责分离。GUI 就绪不要求所有元素都做成图片，适合文字、色块或原生控件的部分直接用代码实现。

## 1. 盘点界面与复用条件

读取扫描摘要、项目现有界面代码及 UI 素材，按已确认交互整理页面、组件、状态和缺项，避免只看图片目录。

- init 的代表页面包括主菜单、对话/选项；姓名框、快捷操作、回看、存读档、设置及制作等待/停止/继续等按项目已采用的功能纳入。局部改版以指定页面及其关联状态为范围；“改选项 GUI”保持主菜单、对话框和剧情正文原有范围。
- 记录目标尺寸与比例、实际中文字体、可用图标和面板、已有交互行为，以及需要保持的控件入口。适用范围内的页面和状态覆盖完整，不借设计机会增加无关功能。
- 已经获用户确认且仍适用的 GUI 直接复用，只补缺项。已有但尚未确认的 GUI 先展示其实际样式供用户决定，默认主题不自动视为已选定方向。
- 用户明确要求重做，或现有 GUI 不符合本次需求时，进入候选制作；纯文字模式也走此判断，仅免除其不需要的剧情插画。

已有方向获确认的局部调整，记录沿用依据后直接落实受影响界面；只有确需重新定向的部分进入候选与确认步骤。

把盘点和后续选择记在已有 GUI 设计记录中；没有时使用 `authoring/handoff/gui-design/design.md`，保留已有内容。该记录用于设计交接，不代替程序状态。

## 2. 提取 GUI 设计依据

从已确认的项目视觉基准与呈现要求提取配色、字体层次、版式密度、形状与装饰语言；注明采用的参考来源。

角色画风不自动决定按钮或菜单样式。基准缺少 UI 信息时，基于已明确的题材和交互需求给出可比较候选，供用户定向；有方向冲突时先询问。纯文字项目直接从其呈现要求建立 GUI 视觉方向。

## 3. 制作并展示候选

需要选择新方向时，默认制作 2—3 套有实质差异的 SVG 方向。init 每套展示以下代表页；局部改版只展示本次范围内的代表页及关键状态：

- **主菜单**：标题、入口层次、按钮与背景关系。
- **对话/选项代表页**：正文与姓名层次、对话框、选项及当前项目需要的快捷入口；无选项的已确认方案无需新增选择玩法。

各套使用相同尺寸、文本、角色名与样例内容便于比较。差异体现为布局、字体层次、留白和装饰语言，而非只换颜色。可使用已有合适的背景辅助预览，候选样例不代表新增剧情或已完成最终素材。

优先使用项目已有设计目录；没有时将 SVG 与渲染预览保存在 `authoring/handoff/gui-design/candidates/<方向名>/`。候选与正式运行资产分开，保留 SVG 作为可编辑源。

用扫描阶段确认可用的本地渲染或预览能力打开 SVG，检查字体缺字、裁切、层次和对比，再通过当前宿主实际支持的图片展示方式交给用户比较。必要时附同尺寸 PNG 预览；只交 SVG 代码、文件路径或口头描述不算已展示。预览能力缺失时报告具体缺口，保持待展示，不自动安装依赖或宣称用户已看过。

每套附简短差异说明和推荐理由，然后停在用户选择：选一套、组合明确元素或修改后再看。此时尚未进入完整 GUI 制作。

## 4. 确认方向

记录用户选定的候选、对应文件及要求保留或调整的元素，归入既有视觉基准确认环节。仅确认一般项目画风不等于确认某套 GUI。

用户要求混合或修改时更新相关代表页并重新展示，确认后继续。已有适用 GUI 获确认的复用路径也记录选择；无需为每张后续页面重做多套候选。

## 5. 落实界面与资产

1. 固定确认的配色、字体、间距和组件风格，制作本次约定页面，以及控件实际需要的普通、悬停、聚焦、选中、不可用等状态；按控件语义取用，不机械生成全部状态图片。
2. 复用项目原生界面结构、控件和样式，将设计落实为 Ren’Py 界面代码。保留真实操作行为，避免把整张 SVG 截图当成已完成的可交互页面。
3. 按当前 SDK 与项目使用方式选择运行资产格式、尺寸和缩放方式；需要转换的图像保留可编辑源。候选能在预览器显示，不代表可原样用于游戏。
4. 字体核对实际可用性、中文覆盖及已有来源说明；新增图标、面板、装饰等按用途命名并列出使用它的页面或代码位置。候选文件留在设计区，仅正式产物进入创作源与后续接入清单。
5. 按项目既有布局在创作区整合共享界面与素材。先确认既有成果的覆盖影响并保护原件，运行区仍由已有接入机制更新。

### 公共选项界面的外观边界

- 按 [公共桥接契约](../../renpi-coding/references/bridge-contract.md) 复用现有操作与状态。外观放在项目自己的 screen 变体、样式等适用扩展点；受管的公共 Python/RPY 保持由插件维护，项目皮肤不复制通信、任务或重载状态机。
- 保持稳定锚点/选项 ID、动作参数、返回值及现有停止、Continue、Retry、接入和重连入口，按钮状态取真实程序阶段。网络客户端、线程和队列留在公共运行时，不存入 screen 的可保存状态。
- 首屏突出选项与下一可执行操作，明确区分制作、校验、待接入和已加载；任务 ID、文件路径和详细日志可折叠，关键错误与恢复入口保持可见。长中文、键盘焦点、控件可用性属于本页核对项，装饰不遮蔽这些信息。

## 6. 交付给整合

交付确认记录、设计源与已有预览、正式界面代码、资产用途对应、仍缺少的必需项，以及待运行核对的页面和操作。init 返回基础准备，局部修改交回 Coding；此时可报告“GUI 制作就绪，待运行核对”，不是“GUI 已验收”。

init 由 [制作可阅读起点](../build-opening/SKILL.md) 整合，局部修改由 Coding 按受影响范围整合。以下真实检查遵守项目执行约束，暂缓项明确保留待验证，避免要求基础准备先完成一个依赖整合的验证：

- 与选定方案对照实际界面，检查字体缺字、长正文/长选项、换行、遮挡及约定窗口尺寸下的布局。
- 检查鼠标与项目支持的键盘焦点、相关控件状态及真实操作，覆盖约定的读写档、设置和制作状态等页面；在保护用户现有存档的独立样本中进行必要写入验证。
- 保留实际预览或截图及明确缺项。发现偏差修正对应组件，重新核对受影响页面；未选方案和用户确认记录保留。

GUI 实际可用与首个单元可阅读共同构成开场阶段的完成条件。用户随后在正式开始环节审阅交付，不用静态 SVG 代替运行结果。
