# 确认审查依据

先读 [Review 边界](../references/review-contract.md)。先确认“审什么、按什么判断”，再读长材料。

## 输入核对

| 输入 | 核对内容 |
| --- | --- |
| 委派与候选 | 真实任务/分支/位置引用、候选版本、要求修订、审查用途、分配的报告/检查目录 |
| 内容依据 | 本轮原文范围或细纲、用户决定、玩家台词/动作/想法权限、有效前情及来源索引 |
| 工程与演出 | 当前完整 RPY、调用方/公共定义、素材清单及真实文件、GUI/视觉基准、音乐使用表、立绘映射 |
| 变更依据 | 新单元或修订类型、原采用版本/差异、本轮刻意保留范围、受影响调用与资源 |
| 验证与旧审查 | 实际 SDK 版本、编译/lint/运行证据、已知限制；复审另含原问题与 Coding 的修复说明 |

缺少某项先判断是否适用：无配音就不要求配音报告；没有变更基线就明确缺失，别猜一个旧文件作为基线。任务、版本或来源不明到足以影响判断时，请 Coding 补充；仍可完成的独立只读检查继续，结论保留真实缺口。

## 阅读顺序与范围

1. 先读本轮要求、变更摘要与产物清单，再实际打开候选文件。作者摘要用于导航，不替代代码/正文。
2. 沿来源引用读取本轮原文/有效前情。祖先资料、当前增补、候选内容、未选路线分开；全篇源资料中的未来事件不算当前角色已知事实。
3. 读取本轮正文及相邻接续、被改定义的引用方、受影响素材/界面。共享定义影响多个分支时沿实际引用扩展范围，不止看当前目录。
4. 对照 Coding 指定检查集，补充由真实变更引出的遗漏并说明原因。采用“要求 → 当前产物/位置 → 检查/证据”的短表，不创建新的产品验收体系。
5. 确认必要证据属于哪些阶段：候选的编译/演出/兼容检查与接入后恢复区分。已匹配的有效证据可检查后引用，避免重复跑相同内容。

## 完成条件

形成足够继续审查的范围、依据和证据缺口，直接填入后续报告的输入/覆盖部分，无需再建一套状态文件。总体门槛与局部咨询目的明确，输出权限明确，进入 [正文检查](../review-story-content/SKILL.md) 与 [整合检查](../review-renpy-integration/SKILL.md)。
