# 报告与复审

按 [判定规则](../references/review-contract.md#判定规则) 汇总，而非按问题条数或平均分决策。一项实质缺陷不被其他通过项抵消；必要证据缺失也不靠自信评分补足。

## 交付一份可执行报告

沿用宿主实际报告格式。没有现成文稿格式时，在 Coding 分配位置使用 [报告模板](../references/report-template.md)，文件名可用 `review-report.md`；这只是内容组织，不新增 JSON schema 或业务 API。

每个确定问题含稳定编号、类型/影响、当前文件与位置、违反依据、实际与期望、证据或复现方式、最小修复目标、复验条件。截图给画面区域及对应场景；内容差异同时给源文位置。需要改多处的同根因合并，保留全部受影响位置。

建议与受阻项分开：建议不变成接入条件，受阻项说明缺何种材料/设施以及如何补齐。对责任角色的意见只交 Coding，不直接派单或改稿。

## 复审流程

1. 接收 Coding 的新候选与修复说明，核对身份、要求及写入已经结束。把旧报告作为问题索引，不把旧通过结论当作新版本结论。
2. 逐条读取实际修复和证据，记录“已解决 / 未解决 / 被新变更替代及其依据”。作者说已修复不等于已验证；删除症状但保留同一根因仍是未解决。
3. 检查修复的直接影响：例如换 tag 的所有显示点、改文本映射的说话者/记忆、换曲后的持续/退出行为、改调用链后的旧档范围。保留适用的未受影响证据引用，不重开全部项目。
4. 新发现只在有明确依据和当前影响时列入；不因复审又出现新的个人风格偏好而无限加项。按当前候选重新给单一总体结论。
5. 修复额度由 Coding 管理；额度用尽仍如实交付未解决事项，Review 不重启制作或自行重置轮次。

## 交回后

通过报告只是 Review 门槛证据，Coding/程序仍核对取消、补充、候选版本和实际衔接，并确认接入后阅读恢复。原文、素材、业务状态和已采用文本记忆保持原责任；审查报告不自行采用内容。

报告写入完成后返回真实任务引用、判定、文件/证据清单及待办。执行失败如实返回失败或受阻信息；取消/过期报告保留原目标，交回程序判定适用性。完成本轮后停止。
